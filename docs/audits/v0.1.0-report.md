# v0.1.0 release audit

## Result

The release candidate is validated through TASK-017. Every Definition of Done item
in spec §27 has executable evidence below. Validation ran before any release tag was
created; TASK-018 remains the only story authorized to create `v0.1.0`.

### Preserved upstream features

- Masterminds-style Select, Insert, Update, Delete, expression, statement-builder,
  prefix/suffix, join, and placeholder APIs.
- Masterminds v1.5.4 `Case` semantics.
- n-r-w final-pass nested placeholder composition.
- CTE, recursive CTE, DML CTE, `UPDATE ... FROM`, nested subqueries, Exists/NotExists,
  scalar comparisons, Not, Coalesce, aggregate expressions, Range, and PostgreSQL
  `In`/`NotIn` behavior.
- Immutable-style builder reuse through `github.com/lann/builder`.

### Removed features

- Database execution, runner, scanning, row, and statement-cache APIs.
- Search and pagination policies.
- Conditional ordering and numeric sort-key mapping.
- `EqNotEmpty` zero-value omission policy.
- Stateful Select table-alias rewriting helpers.
- Root integration infrastructure dependencies and non-standard test assertions.

### Compatibility differences vs Masterminds v1.5.4

- The module import path is `github.com/muonsoft/squirrel`.
- Database execution and statement-cache APIs are intentionally absent.
- PostgreSQL-oriented builder primitives inherited from n-r-w are additional APIs.
- `In`/`NotIn` multi-item slices use a single PostgreSQL array argument with ANY/ALL.
- The complete exported-symbol decisions are documented in
  `docs/API_COMPATIBILITY.md`; the migration fixture covers typical import-only
  builder migrations.

### Regression bugs covered

- Continuous Dollar numbering across parent and child SELECTs.
- Nested builders in Eq, joins, `FromSelect`, columns, update values, And/Or trees,
  prefixes, suffixes, and custom Sqlizers.
- Escaped PostgreSQL question-mark operators without consumed arguments or numbering
  gaps.
- Continuous numbering through multiple, recursive, and DML CTEs.
- CTE and `UPDATE ... FROM` argument ordering.
- Immutable reuse of a base builder.
- Invalid SELECT, INSERT, CTE, expression, nested Sqlizer, and placeholder errors.
- Placeholder replacement and representative composition fuzz coverage.

### PostgreSQL integration scenarios

The integration suite contains executable coverage for:

- simple and nested SELECT;
- correlated EXISTS;
- CTE and recursive CTE;
- `UPDATE ... FROM` and DML CTE;
- `FOR UPDATE SKIP LOCKED`;
- INSERT, UPDATE, and DELETE with RETURNING;
- IN/NOT IN and ANY/ALL, including typed UUID slices;
- JSON question-mark operators;
- CASE and COALESCE.

TASK-017 executed every scenario against PostgreSQL 18.1
(`18.1 (Debian 18.1-1.pgdg13+2)`). The integration command used a non-empty
`POSTGRES_TEST_DSN`; no test was accepted as a skip.

### Remaining risks

- `github.com/lann/builder` remains the immutable-builder implementation. The typed
  replacement opportunity and its compatibility risks are evaluated in
  `docs/TYPED_BUILDER_EVALUATION.md`.
- Arbitrary custom Sqlizers that return pre-numbered `$N` placeholders cannot be
  renumbered by a parent builder; custom nested fragments must return `?`.
- The PostgreSQL ANY/ALL behavior of `In`/`NotIn` is intentionally retained but may
  surprise callers expecting placeholder expansion.
- Identifiers and raw SQL text are trusted-input surfaces; placeholders protect
  values, not identifiers.
- PostgreSQL integration is PostgreSQL-specific by design; no compatibility claim is
  made for other database engines.

### Recommended follow-up work

- After the human release-candidate milestone, run TASK-018 to promote the changelog,
  create the release commit, and create the annotated local `v0.1.0` tag.
- Review upstream changes periodically and port only focused, regression-tested fixes.
- After v0.1.0 is released, evaluate the typed builder replacement as the separate
  evidence-gated stream described in `docs/TYPED_BUILDER_EVALUATION.md`.
- If PostgreSQL-specific helpers expand materially, evaluate a separate
  `squirrel/postgres` package instead of broadening the root API.
